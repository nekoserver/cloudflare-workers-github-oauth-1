SaaS integration map

PR要約パイプラインが各SaaSに持たせている役割

Cloudflareの3コンポーネント(本体Worker・D1・Workers AI)は1つの基盤としてまとめて囲み、 GitHubとSlackはそれぞれ独立した外部SaaSとして輪で囲んだ。dynamicneko・ cf-authが本体Workerへ直接通信することはなく、毎ビルドで実際にGitHubへ pushするだけ。本体Workerが受け取るのはGitHub発のWebhookのみで、そこからビルド通知をSlackへ、 コミットログの要約をWorkers AI→D1へと振り分ける。D1の要約テーブル更新を受けて、 cf-authがその要約を読み出して表示する。

各コンポーネントの役割と現状

GitHub外部SaaS

PRの作成・更新をWebhookで通知させる「発火源」。HMAC署名でなりすましを防ぐ窓口も兼ねる。

現状: 維持 — /webhook/github 1本で全リポジトリのイベントを受け続けている

Slack外部SaaS

要約をBlock Kitで通知し、「詳細を見る」ボタンからモーダルでD1の全情報を見せる「表示面」。

現状: 維持 — POST /slack/interactions が署名検証してモーダルを都度組み立てる

Workers AICloudflare

本体Workerが受け取ったコミットログを渡すと日本語要約を返す「生成エンジン」。コミットごとの要約生成そのものを丸ごと一任している。

現状: 維持 — AI_MODELで切替可能、未設定時はデフォルトにフォールバック

Cloudflare D1Cloudflare

要約結果・失敗理由・自動診断・人手フィードバックをすべて記録する「台帳」。更新されるたびにcf-authが読み取り専用で参照しに来る共有DB。

現状: 維持 — ai_summary_log / ai_summary_reviews の2テーブルに一本化

本体 WorkerCloudflare

GitHub/Slackとの通信を一手に引き受ける「中枢」。dynamicneko・cf-authの毎ビルドwebhookも受け、Slackへのビルド通知とWorkers AIによるコミットログ要約→D1格納を担う。

現状: 維持 — src/index.ts の/webhook/githubハンドラが全処理を統括

dynamicneko / cf-auth

本体Workerとは別デプロイの2つのWorker。本体Workerへの直接通信は持たず、毎ビルドで自分のGitHubリポジトリへpushするだけ。そのpushをGitHubがWebhookとして本体Workerへ中継し、Slackへのビルド通知とWorkers AIによる要約→D1格納につながる。

現状: 維持 — cf-authはさらにD1の要約テーブル更新を読み出して自ページに表示する

役割が固まるまでの主な変化

対象やったこと今の役割への効き目
GitHub App Webhook基盤を先に構築し、後からpull_request分岐を同じ窓口に追加 「イベント種別が増えても受信口は1つ」という設計が今も踏襲されている
Workers AI diffが空だと要約自体がスキップされNULLになる不具合を修正 diff取得に失敗してもタイトル・本文からのフォールバック生成が今の標準動作。コミット単位の要約はAIに一任したまま
Cloudflare D1 ログテーブルを2段階で拡張(基本ログ→resolved/tags/reviews) 失敗時の自動診断(auto-diagnosis)が常時記録される状態を維持
Slack plain textからBlock Kit化し、外部URL遷移をモーダルに置き換え Slackを離れずに要約全文を確認できる体験が定着
dynamicneko / cf-auth 別Workerとして分離。本体Workerへの直接通信は持たせず、毎ビルドで自分のGitHubリポジトリへpushする形に統一 本体Workerを止めずに実験的機能(dynamicneko)や認証専用処理(cf-auth)を独立運用しつつ、GitHub発のWebhook1系統だけでビルド通知とコミット要約を一元化できる
cf-auth → D1 要約テーブル(ai_summary_log)の更新を読み取り専用で参照する経路を追加 cf-auth側にコード変更なしで、D1更新のたびに最新のコミット要約を表示できる
