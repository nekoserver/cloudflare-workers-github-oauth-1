LAYER 01 / NATIVE GH

gh でほぼ同じことができる

専用サブコマンド、または短いAPI呼び出しで置き換えられます。

リポジトリ一覧・名前取得

gh repo list

名前、説明、言語、Star、Fork、更新日時、公開状態を一覧化します。

見やすい一覧
gh repo list --limit 1000 \ --json name,nameWithOwner,url,description,primaryLanguage,stargazerCount,forkCount,updatedAt,isPrivate \ --jq '.[] | [.updatedAt, .nameWithOwner, .isPrivate] | @tsv'
アプリと同じ所属条件
gh api -X GET /user/repos \ -f sort=updated -f visibility=all \ -f affiliation='owner,collaborator,organization_member' \ -f per_page=100 --paginate --jq '.[].full_name'
使い分け: 手軽さなら gh repo list、RESTパラメーターまで合わせるなら gh api。

新規リポジトリ作成

gh repo create

Public／Privateを選び、ページと同じくREADME付きで初期化します。

Public
gh repo create my-new-repo --public --add-readme
Private + 説明
gh repo create my-new-repo --private --add-readme \ --description 'リポジトリの説明'
ポイント: ページは auto_init: true なので、同じ初期状態にするには --add-readme を付けます。

最新コミット

gh api

デフォルトブランチの最新SHAとGitHub上のURLを1件だけ取得します。

gh api -X GET repos/OWNER/REPO/commits -f per_page=1 \ --jq '.[0] | {sha, url: .html_url}'

コミット履歴の参照

gh api

直近20件を、作者・日時・メッセージ・マージ判定付きで整形します。

gh api -X GET repos/OWNER/REPO/commits \ -f per_page=20 -f page=1 \ --jq '.[] | {sha, message: .commit.message, author: (.author.login // .commit.author.name), date: .commit.author.date, isMerge: ((.parents | length) >= 2), url: .html_url}'
マージだけ
gh api repos/OWNER/REPO/commits --paginate \ --jq '.[] | select((.parents | length) >= 2)'
gh repo commitsという一般的な専用コマンドはないため、リモート履歴にはgh apiを使います。clone済みならgit logも選択肢です。

Issue＋PR件数

repository API

ページと同じ合算値はリポジトリ情報のopen_issues_countです。

gh api repos/OWNER/REPO --jq '.open_issues_count'
内容を別々に見る
gh issue list --repo OWNER/REPO --state open --limit 100 gh pr list --repo OWNER/REPO --state open --limit 100

GitHub App権限

gh api

インストールされたAppの対象範囲と権限を確認します。

gh api /user/installations --paginate \ --jq '.installations[] | {id, app_slug, repository_selection, permissions}'
OAuthスコープの概況はgh auth status、レスポンスヘッダーまで見るならgh api -i /user。

Webhook確認

gh api

Webhookを列挙し、アプリと同じようにSlack送信先も判定できます。

gh api repos/OWNER/REPO/hooks --paginate \ --jq '.[] | {id, active, url: .config.url}'
Slackだけ
gh api repos/OWNER/REPO/hooks --paginate \ --jq '.[] | select(.config.url | contains("hooks.slack.com"))'
LAYER 02 / API COMPOSITION

gh api なら再現できる

ページネーション、期間指定、集計まで含む機能です。

月別・日別コミット

since / until

JSTの月初から翌月月初までを取得します。日別ならuntilを翌日にします。

gh api -X GET repos/OWNER/REPO/commits \ -f since='2026-08-01T00:00:00+09:00' \ -f until='2026-09-01T00:00:00+09:00' \ -f per_page=100 --paginate \ --jq '.[] | [.commit.author.date, .sha, .commit.message] | @tsv'
時差: ページはJST境界で再判定します。UTCの日付部分を切るだけでは深夜帯が一致しません。

総コミット数

Link header

1ページ1件で要求し、Linkヘッダーのrel="last"にあるページ番号から推定します。

gh api -i -X GET repos/OWNER/REPO/commits -f per_page=1
Link内のpage=N; rel="last"のNが推定総数です。ヘッダーがなければ0または1件です。

Appインストール状況

installation API

selectedのインストールについて、選択リポジトリを取得します。

gh api /user/installations/INSTALLATION_ID/repositories --paginate \ --jq '.repositories[].full_name'
トークン種別とApp権限によりアクセスできない場合があります。

外部サービス連携判定

app_slug + hooks

Cloudflare／VercelはAppのslug、SlackはWebhook URLから判定します。

gh api /user/installations --paginate \ --jq '.installations[] | select(.app_slug == "cloudflare-pages" or .app_slug == "cloudflare-workers-and-pages" or .app_slug == "vercel") | {app_slug, repository_selection, permissions}'
ページと同じバッジにはrepository_selectionのall／selectedも解釈します。
LAYER 03 / APP DATA

このアプリ独自の機能

GitHub外のD1データや表示モデルを使うため、完全一致するghコマンドはありません。

全リポジトリ横断コミット検索

近似: gh search

アプリはD1キャッシュを部分一致検索します。GitHub側を探す近似例です。

gh search commits '検索語' --repo OWNER/REPO
API取得後にローカル検索
gh api repos/OWNER/REPO/commits --paginate \ --jq '.[] | [.sha, .author.login, .commit.author.name, .commit.message] | @tsv' \ | rg -i '検索語'
非等価: gh searchはGitHubの検索インデックス、ページはワークスペースのD1キャッシュが対象です。

検索履歴

D1 only

検索語、ヒット数、対象リポジトリ、ヒットコミットをD1へ保存します。

# 完全対応する gh コマンドはありません # 近似: 結果を自前で保存 gh search commits '検索語' --json sha,repository,message \ > commit-search-$(date +%Y%m%d-%H%M%S).json

リポジトリの色・グループ

D1 only

色、タグ、アプリ内グループはGitHub属性ではありません。Topicsで近似できます。

gh repo edit OWNER/REPO --add-topic team-platform gh search repos --topic team-platform --owner OWNER
Topicsとアプリのグループは別データなので、ページの色やグループは更新されません。

Zanzibarタプル／ツリー

app model

権限やOAuthスコープを関係モデルへ変換したアプリ固有表示です。

# 元データの一部だけを確認 gh api /user/installations --paginate \ --jq '.installations[] | {app_slug, repository_selection, permissions}'

キーワード分類・共起キーワード

D1 + classifier

検索語の分類と共起語フィルターはアプリ内分析です。

# 素材となるコミットメッセージの取得までが gh の役割 gh api repos/OWNER/REPO/commits --paginate \ --jq '.[].commit.message'

Cloudflareセットアップ通知

Cloudflare side

新規作成後にD1へ未設定通知を保存し、ダッシュボードへ誘導する独自フローです。

# GitHub CLIに対応コマンドはありません # Cloudflare CLIによる別操作 npx wrangler pages project create
wranglerはghではなくCloudflareのCLIです。通知の消化や連携判定とも別操作です。
LAYER 04 / MISSING ON PAGE

gh コマンドにあってリポジトリページにない機能

GitHub CLIでは日常的に使うが、このアプリのリポジトリページにはメニュー・画面が存在しない操作です。実装するなら、どのAPI呼び出しをどの画面要素に対応させるかを併記しています。

PR作成・マージ

gh pr create / merge

ページにはIssue＋PRの件数表示（issues-pr）はあるが、PRを作成・レビュー・マージする画面がありません。

gh での操作
gh pr create --repo OWNER/REPO --base main --head feature/x \ --title 'タイトル' --body '本文' gh pr merge 123 --repo OWNER/REPO --squash --delete-branch
実装案: リポジトリ詳細カードに「PR」タブを追加し、一覧は GET /repos/{owner}/{repo}/pulls をD1にキャッシュせず都度取得（PRは状態変化が速いため）。作成は POST /repos/{owner}/{repo}/pulls、マージは PUT /repos/{owner}/{repo}/pulls/{number}/merge をWorker経由でプロキシし、GitHub Appのpull_requests権限（write）が付与されている場合のみボタンを活性化する。マージ操作は破壊的なので確認モーダル必須、かつ監査目的で実行者・結果をD1の操作ログテーブルへ記録する（ルール8の記録義務）。

Issue作成・クローズ

gh issue create / close

Issue件数の合算値は表示されますが、個別のIssueを作成・編集・クローズする手段がありません。

gh issue create --repo OWNER/REPO --title 'タイトル' --body '本文' gh issue close 45 --repo OWNER/REPO --reason completed
実装案: issues-prカードの詳細展開に一覧（GET /repos/{owner}/{repo}/issues、pull_requestキーで絞り込んでPRを除外）を追加。作成フォームは最小限（title/body/label）にとどめ、POST .../issues を叩く。クローズ時は state_reason を必須選択（completed/not_planned）にして、ghの挙動（ルール文中で言及される「closingの際にstate_reasonを設定」）に合わせる。権限はGitHub Appのissues権限を確認してからUIを出し分ける。

リリース管理

gh release list / create

最新コミットやコミット履歴は見られますが、タグ付きリリースの一覧・作成・アセット公開は非対応です。

gh release list --repo OWNER/REPO --limit 20 gh release create v1.2.0 --repo OWNER/REPO \ --title 'v1.2.0' --generate-notes
実装案: リポジトリカードに「Releases」セクションを新設し、GET /repos/{owner}/{repo}/releases を一覧表示（D1に軽くキャッシュしてOK、リリースは頻度が低い）。作成は POST .../releases を叩くフォームとし、generate_release_notes: true をデフォルトにしてghの--generate-notesと同等の体験にする。タグが存在しない場合はcloneせずに作れないため、対象コミットSHAをtarget_commitishで指定できるようにする。

Actionsワークフロー実行・ログ

gh workflow run / gh run view --log

CI/CDの実行トリガーや失敗ログの確認画面がなく、GitHub側を直接見るしかありません。

gh workflow run deploy.yml --repo OWNER/REPO --ref main gh run list --repo OWNER/REPO --limit 10 gh run view RUN_ID --repo OWNER/REPO --log-failed
実装案: GET /repos/{owner}/{repo}/actions/runs と .../actions/workflows を組み合わせて実行履歴カードを作る。手動トリガーは POST .../actions/workflows/{workflow_id}/dispatches（workflow_dispatchイベントが定義されているワークフローのみ対象）。ログ取得は容量が大きいため全文表示せず、失敗ジョブのログだけを GET .../jobs/{job_id}/logs でオンデマンド取得し、モーダルに表示する。GitHub Appのactions権限（read/write）の有無で機能を出し分ける。

Secrets管理

gh secret set / list

Cloudflare通知（cloudflare）はあるものの、リポジトリのActions Secrets自体を見る・設定する機能はありません。

gh secret list --repo OWNER/REPO gh secret set MY_SECRET --repo OWNER/REPO --body 'value'
実装案: 値そのものは取得APIが存在しない（GitHub側の仕様）ため、一覧はGET /repos/{owner}/{repo}/actions/secretsで名前・更新日時のみ表示。設定にはlibsodiumでの公開鍵暗号化（GET .../actions/secrets/public-keyで鍵取得後、暗号化してPUT）が必須なので、Workers環境でも動くWebCrypto／tweetnacl相当のライブラリを選定する。誤って平文をログや履歴に残さないよう、送信フォームの値は画面上でもマスクし、D1にも保存しない（ルール4の平文禁止と同じ思想を秘密情報全般に適用）。

ブランチ保護ルール

gh api branches/.../protection

保護ルール（必須レビュー数、ステータスチェック必須化など）の閲覧・変更画面がありません。

gh api repos/OWNER/REPO/branches/main/protection gh api -X PUT repos/OWNER/REPO/branches/main/protection \ -f required_pull_request_reviews[required_approving_review_count]=1
実装案: リポジトリ詳細に「Branch protection」タブを追加し、GET .../branches/{branch}/protection で現在の設定を読み取り専用表示するところから始める（変更は影響が大きいため段階導入）。編集を実装する場合はPUTのペイロードが多階層になるため、フォームではなく主要項目（必須レビュー数・ステータスチェック必須・force push禁止）に絞ったチェックボックス群にとどめ、生JSONは出さない。管理者権限（admin:true）を持つトークン/Appのみ操作可能にする。

ラベル管理

gh label list / create

Issue/PRに付けるラベルの一覧・作成・色変更を行う画面がありません。

gh label list --repo OWNER/REPO gh label create bug --repo OWNER/REPO --color FF0000 \ --description 'バグ報告'
実装案: issue-manage・pr-manageの作成フォームで使うラベル選択肢として、GET /repos/{owner}/{repo}/labels を軽くD1キャッシュ（更新頻度が低いため数時間TTLで十分）。新規作成・色変更まで対応するならPOST / PATCH .../labels/{name}を叩く簡易フォームを設け、色はカラーピッカーでHEXを直接指定させる（グループ機能で使う色定義とは別データである点をルール26と同様に明示すること）。
OWNER/REPO、INSTALLATION_IDなどのプレースホルダーを実値に置き換えて実行してください。
